# fndgx SEQS 实验 —— 32 试过,否决,已退回 8(2026-09-20)

栈:`stacks/fndgx`(S2 `100.67.164.92:18300`,served name `qwen3.8-flash-next`)
基线:`benchmarks/fndgx-2026-09-20/`(同一天、同一套脚本、同样解锁时钟、`SEQS=8`)
脚本:`concurrency-seqs.py` —— 基线 `concurrency.py` 的直系版本,**请求形状逐字相同**
(同样 8 道题、`max_tokens=400`、`temperature=0`、非流式、`enable_thinking=false`、
每个并发位不同 prompt),只加了梯子长度可配、每级量主机内存、每级采 PLE 计数器。

**结论:`SEQS=32` 在 c8 及以下没有收益,已退回上游默认 8。**
唯一留下的改动是 `PROM_MULTIPROC=1`(导出 PLE 计数器,不动任何配方参数)。

---

## 1. 当初的假设,以及它为什么是外推

基线梯子在 c8 封顶 112.4 tok/s,c12/c16 不再增长,只有延迟在涨。解除时钟上限
只把峰值推动 +1.2%,却把 c4 每流推了 +9.5% —— 看起来封顶的是 `max_num_seqs=8`。

支持这个假设的是上游 README 引的 @jschmied 梯子:聚合一路涨到 **c48 = 266.8**,
每 token 缺页代价降 4.4 倍。

⚠️ **但那条梯子是另一套配置** —— 无投机解码、用 vLLM 原生 PLE CPU offload、
8k 上下文,上游自己在表头标注了。上游对**本配方**(hybrid + MTP=2 + RadixArk)
真正发布过的并发数据**只有一个点**:c4 每流 21.6 tok/s。

也就是说这个假设从一开始就是**跨配置外推**,不是「上游说会涨」。
`docs/gb10-tuning-cn.md` §6 的标准教训正是这一条:别人 GB10 上的结果,在这两台
机器上复现之前只是假设。第二个 QSFP 口那次也是这么倒的。

---

## 2. 实测

`--max-num-seqs` 按 `docker inspect` 验过确实是 32(vLLM 自己的 `non-default args`
行也是 `'max_num_seqs': 32`)—— 不是只看启动横幅,那是 gotcha #9 的形状。

| 并发 | 聚合(SEQS=32) | 每流 | 延迟 中位/最慢 | 基线(SEQS=8) | 差 |
|---:|---:|---:|---|---:|---:|
| 1 | 44.6 | 44.6 | 3.7 / 3.7 s | 44.5 | +0.1% |
| 2 | 67.8 | 33.9 | 9.2 / 10.2 s | 67.8 | +0.1% |
| 4 | 93.8 | 23.5 | 13.8 / 14.2 s | 92.1 | +1.9% |
| 6 | 91.2 | 15.2 | 15.1 / 18.4 s | 93.8 | −2.7% |
| 8 | 104.5 | 13.1 | 20.0 / 23.4 s | 112.4 | **−7.0%** |

主机可用内存全程 11.2–11.9%,没有接近 memwatch 的 warn=8%。

**c1/c2 复现到 +0.1%** —— 这套 harness 在低并发是稳的。所以 **c8 的 −7% 大于噪声,
且未解释**;单次测量,没有重复。

### ⚠️ 只测到 c8 —— 结论的准确边界

按要求封顶在 c8。所以成立的说法是「**c8 及以下无收益**」,**不是**「SEQS 对更高
并发无用」。而且 c8 及以下两种配置**本来就都不排队**(8 ≤ 8,8 ≤ 32),几乎注定
一样 —— 这一组更像回归检查,而不是对假设的检验。**c12 以上没测过。**

### 启动期:SEQS 不吃 KV 池 —— 但 KV 池本身**逐次启动在变**

| 启动 | 配置 | GPU KV cache size | Maximum concurrency |
|---|---|---|---|
| 1(基线) | SEQS=8 | 496,770 tok | 1.90x |
| 2 | SEQS=32 | 498,218 tok | 1.90x |
| 3(退回后) | **SEQS=8,与启动 1 完全同配置** | **534,426 tok** | **2.04x** |

`consumed (weights + non-torch)` 81.85 / 81.78 GiB,CUDA graph 27 个形状。

**SEQS 不吃 KV 池** —— 启动 1 vs 2 差 0.3%,这条成立。

⚠️⚠️ **但启动 1 vs 启动 3 是同一个配置,池子差了 +7.6%(496,770 → 534,426)。**
这是本轮最意外的一条,而且它直接打在「我们比上游 RadixArk 低 15%」这个长期
未解之谜上:

| | KV 池 | vs 上游 589K |
|---|---|---|
| 上游 RadixArk | 589,000 | — |
| 我们,启动 1 | 496,770 | −15.7% |
| 我们,启动 3 | **534,426** | **−9.3%** |

也就是说**那个「15% 缺口」里至少有 7.6 个点是逐次启动的抖动,不是稳定缺口**。
这与既有假设方向一致且是第一条实测证据:`GPU_MEM` 是**总**显存的比例而非空闲
的比例(上游 serve.sh 原话),所以启动瞬间别的进程占了多少,直接决定池子大小。
S2 上常驻 k3s server + Cilium + 桌面 + node-exporter,它们的 RSS 本来就在动。

⏳ **仍然没做的验证**:停 k3s/桌面 → 重启 → 读 `Available KV cache memory`。
⚠️ 且别忘了 glm53 那次把 k3s 整个停掉只换回 0.11 GiB —— 方向对不代表量级对。
⚠️ **今后引用本栈 KV 池的任何数字都要写清是哪一次启动**;单次读数不足以
支撑「缺口多少」这种结论,n=3 才刚够看出它在动。

## 3. PLE mmap 计数器 —— 本仓库第一次有这组数

`PROM_MULTIPROC=1` 打开后 `/metrics` 多出 8 条 `vllm:ple_mmap_*`。
在此之前本仓库**没有任何指标**能看到 mmap 的 48 GiB PLE 表的代价。

| 并发 | 每 token PLE 开销 | gather 占 op | op 占墙钟 | 每 token 行数 |
|---:|---:|---:|---:|---:|
| 1 | 2.13 ms | 79.1% | 9.6% | 26.2 |
| 2 | 1.34 ms | 77.6% | 9.1% | 24.0 |
| 4 | **0.99 ms** | 76.8% | 9.3% | 26.5 |
| 6 | 1.20 ms | 81.1% | 10.9% | 26.8 |
| 8 | 1.12 ms | 82.4% | 11.7% | 21.3 |

每 token 查的行数基本恒定(21–27),所以每 token 成本从 c1 的 2.13 ms 降到 c4 的
0.99 ms(**2.2×**)是**每行更便宜**,不是查得更少 —— 上游「并发越高缺页越便宜」
的方向在这台机器上复现了(上游是 c1→c48 降 4.4 倍,我们只覆盖到 c8)。

⚠️ **这组数推翻了本仓库自己的一个猜测。** 页缓存只有约 12–13 GiB 而 PLE 表 48 GiB,
据此曾把「页缓存不够」列为头号瓶颈嫌疑。实测 PLE 查表只占引擎墙钟的 **9–12%** ——
就算归零也换不来多少。据此:
- 「降 `GPU_MEM` 到 0.75 换页缓存」这条建议**失去了依据**,不要再做;
- `PREWARM=1` 的预期收益同样被压到很小。

⏳ `op_seconds` 是否跨 32 个 worker 线程累加,**没有确认** —— 所以 9–12% 是下限
还是上限还不知道。要定这件事得读 `src/` 里计数器的实现。

## 4. 对上游:凡是上游发过数的轴,都符合或更好

上游 README「Checkpoints」一节有 RadixArk 专列。逐项:

| 轴 | 上游 RadixArk | 我们 | 判定 |
|---|---|---|---|
| 单流 greedy 散文 | 37.1 tok/s | 35.3 | −4.9% ✅ |
| **4 并发,每流** | 21.6 tok/s | **23.5** | **+8.8%,反超** ✅ |
| prefill 热 | 2,400–2,900 @8k / 2,500–3,000 @32k | 2,385 @13.0K / 3,050 @51.7K | 相符或超上沿 ✅ |
| prefill 冷 | 8k: 5.1 s = 1,569 tok/s | 1,482 @10.6K | prompt 长 33%,速率 94% ✅ |
| T=0 确定性 | yes | yes | ✅ |
| KV 池 @`GPU_MEM=0.80` | **589k tok** | 496,770 / 498,218 / **534,426**(三次启动) | **−9.3%~−15.7% ❌ 部分是启动抖动,见 §2** |

⚠️ 上游模式表另给 hybrid「~630k tokens」,按那个算是 −21%,**更差不是更好**。

KV 缺口拆成两段,别合并:
- **679k → 589k 是 RadixArk 自己的已知代价**,我们的启动日志点名:
  `modelopt block-moe: experts mtp.layers.48.mlp.experts -> checkpoint algo None`。
- **589k → 498k 是我们自己的,仍未解释。** 最可能是 `GPU_MEM` 按**总**显存算,
  而 S2 启动时已被占掉 8.5 GiB(`Free memory on device 113.18/121.69 GiB`)。
  ⚠️ 别当结论:glm53 那次把 k3s 整个停掉只换回 0.11 GiB。

**上游发布了、我们没测的**(所以「符不符合」无从谈起):tournament 质量
86.1% ± 1.9、needle 100k/185k/323k/413k 4/4、prefill at 185k/323k/413k
(1,919 / 2,497 / 2,856 tok/s)。我们最长只喂过 51.7K。

**c8 聚合上游没有对应项** —— 见 §1。

## 5. 落到配置上

`stacks/fndgx/launch.sh`:
- `SEQS=8` —— 退回上游默认,理由记在该文件的注释里
- `PROM_MULTIPROC=1` —— **保留**,§3 的数据就是它给的,且不动任何配方参数
- `--long-prefill-token-threshold` —— **仍未动**。它是 TTFT/响应性的滑块
  (上游测 1024 会让单流 8k prefill −36%),与吞吐是两件事,要单独评估
